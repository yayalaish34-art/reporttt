# מערכת הפקת דוחות קרינה

הפקת דוחות בדיקת קרינה אלקטרומגנטית (ELF ו-RF) ממסמך Word עם שדות דינמיים.

## הפעלה ראשונה

```bash
npm install
npm run build:template     # בונה את התבנית ממסמך המקור
npm run seed:all           # תבנית + לקוח לדוגמה + חתימות ממסמך המקור
npm run dev                # http://localhost:3000
```

ניסוח עם AI הוא רשות. כדי להפעיל אותו, העתיקו את `.env.example` ל-`.env.local`
ומלאו `OPENAI_API_KEY`. בלעדיו האפליקציה עובדת במלואה — הנוסח נבנה מהנתונים לפי
כללים, וזה ממילא מסלול ברירת המחדל.

מסמך המקור נמצא ב-`templates/source/report-source.docx` — זהו דוח חתום ומלא, לא תבנית.
שלב `build:template` הוא שהופך אותו לתבנית.

## אחסון — חובה בפריסה

כל מה שהאפליקציה שומרת יושב בקובץ SQLite אחד: הדוחות, **התמונות שהועלו**, התבניות
הפעילות והחתימות. מקומית הוא ב-`data/reports.db` וזה בסדר.

**בפריסה בקונטיינר חייבים volume קבוע.** נתיב ברירת המחדל נמצא בתוך תיקיית
האפליקציה, שנבנית מחדש בכל דיפלוי — כלומר בלי volume המסד נמחק ונוצר ריק בכל
פריסה.

הכשל הזה לא צועק, הוא מתגלה מהצד: הכיתובים של התמונות שמורים ב-JSON של הדוח
עצמו ולכן שורדים, בעוד קבצי התמונות נמחקים. התוצאה היא **דוח שמציג את התמונות
בעורך אך מופק בלי נספח התמונות ובלי שום הודעת שגיאה**.

ב-Railway: מחברים volume לשירות, ממפים אותו ל-`/data`, ומגדירים

```
REPORT_DB_PATH=/data/reports.db
```

`/api/health` מדווח האם זה מוגדר — ראו `storage.durable`. אם לא, מודפסת גם אזהרה
בלוג בעליית השרת.

## איך זה עובד

קובץ `.docx` הוא ארכיון ZIP של קבצי XML. המיזוג הוא פעולת מחרוזות על
`word/document.xml` בתוך הארכיון — בלי Word מותקן, ורץ על שרת Linux בלי בעיה.

```
report-source.docx          דוח חתום, מלא בנתונים אמיתיים
        │
        │  npm run build:template
        ▼
report-template.docx        אותו מסמך, עם {placeholders} ולולאות
        │
        │  npm run seed
        ▼
   DB (templates)           המקור היחיד בזמן ריצה
        │
        │  mergeDocx(template, data)
        ▼
   דוח מוכן .docx
```

### למה שלב בנייה ולא סימון ידני ב-Word

מסמך המקור מכיל 31 פרוטוקולי ELF ו-11 פרוטוקולי RF — כולם חוזרים על אותו מבנה.
סימון ידני ב-Word היה אומר למחוק 40 מקטעים בעכבר ולסמן את מה שנשאר, ולחזור על כל
זה בכל פעם שצוות הסקר מעדכן את נוסח המסמך. הסקריפט עושה את זה מחדש בשנייה.

הסקריפט מוודא שכל עוגן נמצא בדיוק פעם אחת. אם המסמך שונה והעוגן זז — הבנייה
נכשלת עם שם השדה, במקום לייצר בשקט תבנית חצי-מסומנת.

### התבנית חיה ב-DB בלבד

הקובץ ב-`templates/` הוא תוצר בנייה שמשמש לטעינה ראשונית, לא מקור אמת בזמן ריצה.
שני מקורות אמת לאותה תבנית זה מקור קבוע לבאגים — תיקון נכנס לאחד, והשני הוא מה
שבאמת מרונדר.

### עריכת התבנית

יש שני קבצים והם לא שקולים:

| קובץ | מה זה | מתי נוגעים בו |
|---|---|---|
| `templates/source/report-source.docx` | הדוח החתום שממנו נבנית התבנית | שינוי שצריך לשרוד בנייה מחדש |
| `templates/report-template.docx` | תוצר בנייה, לטעינה ראשונית בלבד | אף פעם — נדרס בכל בנייה |
| התבנית ב-DB | **מה שבאמת מרונדר** | שינוי מהיר, בלי deploy |

**לשינוי מהיר** — הורדה מ-`/templates`, עריכה ב-Word, העלאה חזרה. פעיל מיד,
הגרסה הקודמת נשמרת לחזרה אחורה.

**לשינוי שישרוד בנייה מחדש** — עריכת `report-source.docx` ואז:

```bash
npm run build:template && npm run seed
```

⚠️ `build:template` דורס עריכות שנעשו דרך ההעלאה. אם שינוי חשוב נעשה בהעלאה בלבד,
הוא ייעלם ברגע שמישהו יריץ בנייה מחדש.

## סימון שדות ב-Word

במקום להוסיף עוגן טקסט לסקריפט הבנייה, מסמנים ערך ב-Word ונותנים לו שם:

```bash
# 1. פותחים את המסמך ב-Word ומדגישים (Highlight) כל ערך דינמי
npm run scan:fields        # 2. מזהה מה סומן ומציע שם שדה לכל אחד
                           # 3. משלימים שמות שלא זוהו ב-field-map.json
npm run build:template     # 4. כל סימון הופך ל-placeholder
```

### עדיף הדגשה, לא צבע

**הדגשה (Highlight)** היא הסימון המומלץ. דוח מוגמר אף פעם לא יוצא עם טקסט מודגש,
ולכן הדגשה יכולה להיות רק הוראה לבנייה. צבע, לעומת זאת, הוא עיצוב תוכן — במסמך
הזה פסקת ההסתייגות מודפסת באדום כהה בכוונה — ותמיד תישאר השאלה "האדום הזה סימון
או כוונה?".

כל צבע הדגשה מתקבל. גם **צבע טקסט אדום מלא** (`#FF0000`) מתקבל למי שמעדיף.
`#C00000` ("אדום כהה") שמור לתוכן ומתעלמים ממנו.

### שלוש דרכים לתת שם

| מה עושים ב-Word | מתי | מה קורה |
|---|---|---|
| מדגישים את הערך | לשדה קיים עם תווית | הסורק מציע שם לפי התווית או הערך |
| מדגישים ומקלידים `{fieldName}` במקום הערך | **לשדה חדש** | השם נקבע במקום, בלי JSON |
| מדגישים, ומשלימים ב-field-map.json | לשדה חדש בלי שם ברור | ממלאים ידנית |

**הדרך השנייה היא הפתרון לשדות חדשים.** סימון אומר *איפה*, לא *מה* — ולשדה
שהמערכת מעולם לא ראתה אין ממה לנחש שם. הקלדת `{siteName}` בתוך הסימון סוגרת את
העניין במקום, במקום להשאיר שורה ריקה בקובץ JSON לחזור אליה.

### מה הסורק מנחש

| אות | מה נעשה |
|---|---|
| השם כתוב בתוך הסימון | משתמש בו — לא ניחוש |
| הפסקה נושאת תווית ("אפיון המקום:") | מציע לפי התווית |
| הערך מופיע ברשימת השדות | מציע לפי הערך |
| שום דבר לא זוהה | משאיר ריק — **הבנייה תיכשל עד שימולא** |

התווית גוברת על הערך. אותו טקסט יכול להיות כמה שדות — איש הקשר והמבקש הם לרוב
אותו אדם — והתווית אומרת איזה מהם המופע הזה.

סימון בלי שם שדה **מפיל את הבנייה**. סימון שמישהו טרח לעשות ולא קיבל שם הוא כוונה
שאבדה, וטעות שקטה כאן היא שדה שנשאר קשיח לנצח.

### מה נשמר ומה נמחק

- **הסימון עצמו נמחק** — הדגשה וצבע כאחד. הוא אמר "זה דינמי"; אילו נשאר, כל ערך
  ממוזג היה מודפס מודגש או אדום.
- **שאר העיצוב נשמר.** ערך מודגש עם קו תחתון נשאר כזה.
- **הרווחים והפיסוק סביב הערך נשמרים.** `אפיון המקום: משרדים.` הופך ל-
  `אפיון המקום: {siteCharacter}.` ולא ל-`אפיון המקום:{siteCharacter}`.
- **Word מפצל ערך לכמה ריצות** — ריצות מסומנות סמוכות מאוחדות לאזור אחד.

### יחסי גומלין עם העוגנים המובנים

הסימונים מוחלים ראשונים, ולכן כלל עוגן שהערך שלו כבר הפך ל-placeholder מדווח כמי
שהמשימה שלו בוצעה, במקום להיכשל על "עוגן לא נמצא". שתי השיטות עובדות זו לצד זו על
אותו מסמך.

## תחביר השדות בתבנית

| תחביר | מה זה עושה |
|---|---|
| `{fieldName}` | שדה פשוט |
| `{#items}` … `{/items}` | לולאה — חוזרת על הקטע לכל פריט |
| `{^items}` … `{/items}` | תנאי הפוך — מוצג רק אם ריק |
| `{@rawXml}` | הזרקת OOXML מוכן (נספח התמונות) |

לולאה בטבלה: `{#rows}` בתא הראשון של שורת הנתונים ו-`{/rows}` בתא האחרון של אותה
שורה. עם `paragraphLoop: true` הספרייה משכפלת את השורה כולה.

רשימת השדות המלאה מופיעה במסך `/templates`, ליד טופס ההעלאה — מי שעורך את התבנית
ב-Word הוא מי שצריך אותה.

## הכותרת העליונה

הכותרת מודפסת בראש כל עמוד ומכילה שלושה דברים שנגזרים מתאריך אחד — `reportDate`:

| שדה בתבנית | דוגמה | מקור |
|---|---|---|
| `{headerWeekday}` | יום שלישי | `Intl` |
| `{headerHebrewDate}` | ח' תמוז תשפ"ו | גימטריה מקומית + שם החודש מ-`Intl` |
| `{headerDate}` | 23 יוני 2026 | `Intl`, בלי התחילית "ב" |
| `{referenceNumber}` | 2126062303 | שדה חופשי |

`Intl` מחזיר "8 בתמוז 5786" — הספרות המערביות והתחילית לא מתאימות, ולכן המספרים
מאויתים ב-`hebrew-date.ts`. 15 ו-16 נכתבים ט"ו ו-ט"ז ולא י"ה ו-י"ו, והשנה יורדת
מהאלפים (5786 → תשפ"ו). שמות החודשים מגיעים מ-`Intl` כדי שאדר א'/אדר ב' בשנה
מעוברת יהיו נכונים.

התאריך **נשמר** ולא נלקח מהשעון בזמן ההפקה: הפקה חוזרת של דוח שיצא חייבת לשחזר
אותו, לא לתארך אותו מחדש בשקט. בטופס יש תצוגה מקדימה של הכותרת, כי תאריך עברי
שגוי הוא הדבר היחיד שאי אפשר לאמת בעין.

## בלוק הנמען

הלקוח נבחר מספר הלקוחות (`/customers`) ולא מוקלד — זה המקום שבו ערך שגוי הכי פחות
בולט והכי מביך: דוח שממוען לאיש הקשר הקודם בחברה הנכונה נראה תקין עד שמישהו בכיר
רואה אותו.

שני סוגי לקוח:

```
חברה                                לקוח פרטי
────────────────────────            ────────────────────────
לכבוד                                לכבוד
ירון חכם - רמ"ד אחזקה ובינוי         ירון חכם
כרטיסי אשראי לישראל בע"מ  ← מודגש    תפוצות ישראל 13
תפוצות ישראל 13                      גבעתיים          ← מודגש
גבעתיים                   ← מודגש    נייד : 052-2857557
נייד : 052-2857557                   מייל: ...
מייל: ...
```

שם החברה והעיר מודפסים **מודגש עם קו תחתון**. זה לא נוסף בקוד — כך הם מעוצבים
במסמך המקור, ו-`setParagraphText` משמר את ה-`rPr` של ה-run המקורי. הבדיקה
ב-`smoke-recipient.ts` מאמתת `w:b`, `w:bCs` ו-`w:u` בפלט, כי `w:b` לבדו לא מדגיש
טקסט עברי — צריך גם `w:bCs`.

שורת איש הקשר מורכבת ב-`report-mapper.ts` ולא בתבנית, כדי שהמקף לא יישאר תלוי
כשאין תפקיד. שורת שם החברה עטופה ב-`{#isCompany}`/`{/isCompany}` — אצל לקוח פרטי
היא נעלמת לגמרי ולא מרונדרת ריקה, כי שורה ריקה בתוך בלוק הכתובת נראית כתקלת עימוד.

## משפטי הפתיחה

שלושה משפטים בעמוד הראשון מציינים אילו טווחי תדר נבדקו, ובמסמך המקור כל
השלושה היו כתובים ביד:

```
סקר בטיחות קרינה אלקטרומגנטית (אל מ"ג) בתדירויות רשת החשמל ורדיו ב<אתר>
בתאריך <תאריך> בוצעו מדידות לקביעת רמת השדה האלקטרומגנטי בתדירויות רשת החשמל ורדיו ב<אתר>
המדידות בוצעו במכשיר מדידה תקני למדידות ELF ו- RF, ראה פרטים בהמשך.
```

כולם נגזרים כעת משדה אחד — `surveyScope`:

| סוג הסקר | טווחי התדר | מכשור |
|---|---|---|
| `both` | בתדירויות רשת החשמל ורדיו | ELF ו- RF |
| `elf` | בתדירויות רשת החשמל | ELF |
| `rf` | בתדירויות רדיו | RF |

בלי זה, סקר ELF בלבד היה מוציא עמוד ראשון שמצהיר שנבדקו גם תדרי רדיו — שקר
שנקרא תקין לחלוטין. `smoke-wording.ts` מאמת שבסקר ELF המילה "רדיו" לא מופיעה
בעמוד הפתיחה כלל, ולהפך.

### למה כללים ולא AI כברירת מחדל

זהו מסמך ציות. הנוסח קבוע, הרגולטור מצפה לו, ומשפט שמשתנה בין דוח לדוח מזמין את
השאלה איזו גרסה הייתה נכונה. הבנייה לפי כללים חינמית, מיידית, עובדת בלי רשת
ומחזירה תמיד את אותו פלט.

### ניסוח עם AI

כפתור רשות, לאתרים שהדפוס הקבוע מסורבל עבורם — סקר שפרוס על כמה מבנים, או לקוח
שביקש ניסוח מסוים. המודל מקבל את הנוסח הקנוני כדוגמה עובדת ומתבקש לשמור על
הדפוס. התוצאה היא **הצעה**: היא מעבירה את שני השדות למצב "ידני" ומסומנת ככזו,
ותמיד אפשר לחזור לאוטומטי.

שכבת הגנה: נוסח שמזכיר טווח תדר שלא נכלל בסקר נדחה ולא מוצג. זו הדרך היחידה שבה
המודל יכול להזיק כאן, ובודק היה צריך לשים לב לחוסר כדי לתפוס את זה.

מודל ברירת המחדל הוא `gpt-5` עם `reasoning_effort: minimal`. בלי זה הוא שורף את
כל תקציב הטוקנים על הרהורים לגבי משפט תבניתי ומחזיר תשובה ריקה — נמדד: 1205
טוקנים, פלט ריק. עם ההגדרה: ~2 שניות, נוסח תקין. אפשר להחליף דרך `OPENAI_MODEL`.

**המפתח לעולם לא נכנס לקוד.** הוא נקרא מ-`OPENAI_API_KEY` בסביבה, ו-`.env.local`
מוחרג ב-git. שם האתר ותאריך המדידה כן יוצאים החוצה בקריאה — נתוני הלקוח והמדידות
לא. הכפתור מוסתר לגמרי כשאין מפתח.

## חתימות

**זה היה באג.** התבנית משכפלת שורה אחת לכל טבלת אנשים, וכל חתימה שנשארה בתוך
השורה הזו הוטבעה על כולם. במסמך המקור:

| שורה | חתימה במקור | מה שהתבנית ייצרה |
|---|---|---|
| עורך הדוח | `image4.png` | `image4.png` ✓ |
| מאשר הדוח | `image5.png` | `image4.png` ✗ |

חתימה שייכת לאדם, לא לדוח, ולכן היא לא יכולה לשבת בתבנית. תא החתימה הוא כעת
`{@signatureXml}` בתוך הלולאה, וכל שורה מזריקה את שלה. אדם בלי חתימה מקבל תא ריק —
תא ריק נראה כמו משהו שלא הושלם, חתימה שגויה נראית תקינה לחלוטין.

הספרייה ב-`/signatures`. `seed:signatures` מוציא את שלוש החתימות ממסמך המקור
עצמו. השמות כוללים תפקיד ("יורם גבאי — מאשר") כי במקור היו שני סריקות נפרדות של
אותה חתימה, אחת לכל טבלה.

## טבלאות המדידה

"הוספת טבלה" שואל איזה סוג, וטבלה חדשה נפתחת עם 6 שורות ריקות. שני הסוגים נשמרים
ברשימות נפרדות כי המסמך מציב אותם בשני מקטעים שונים — כל טבלאות ה-ELF תחת כותרת
סקר ה-ELF וכל טבלאות ה-RF תחת שלה — ולכן הן לא יכולות להשתלב זו בזו בפלט, איך
שלא יסודרו בטופס.

## המלכודות והפתרון שלהן בקוד

**סדר הפריטים בארכיון.** מפרט OOXML דורש ש-`[Content_Types].xml` יהיה ראשון.
PizZip מסדר מחדש אחרי `render`, ואז Word מציע "לתקן" את הקובץ.
→ `ensureContentTypesFirst`, אחרי `render` ולפני `generate`.

**שדה חסר מדפיס `undefined`.** ברירת המחדל של הספרייה מדביקה את המילה למסמך.
→ `nullGetter` שמחזיר מחרוזת ריקה. היוצא מן הכלל הוא תגית `{@rawXml}` — היא מחליפה
את הפסקה שמכילה אותה, ולכן מחרוזת ריקה תשאיר את ה-body בלי אלמנט חוקי במקום הזה;
היא מקבלת `<w:p/>`.

**Word מפצל שדות.** בודק האיות מפצל `{customerName}` לכמה `<w:r>` נפרדים.
docxtemplater מאחד runs לבד. אם שדה בכל זאת לא מתמלא — מחקו והקלידו מחדש ברצף
אחד. בבניית התבנית הבעיה נמנעת מראש: `setParagraphText` בונה את הפסקה מחדש סביב
run יחיד.

**שדות Word (מספרי עמודים).** בניית פסקה מחדש הייתה מקפיאה את "עמוד 17 מתוך 17"
בכל עמוד. → `hasField` חוסם בנייה מחדש של פסקה שמכילה `fldChar`.

**תמונות דינמיות.** לא נתמכות בגרסה הבסיסית של docxtemplater.
→ `photos.ts` מזריק ידנית: קובץ ל-`word/media/`, relationship ל-`document.xml.rels`,
סיומת ל-`[Content_Types].xml`, ואז OOXML דרך `{@photosXml}`. שלושתם חייבים להסכים,
אחרת Word מציע לתקן — `smoke-photos.ts` בודק את כל השלושה במפורש.

**עברית ו-RTL.** הכיווניות נקבעת בתבנית, לא בקוד. ערך מוזרק יורש את כיווניות
הפסקה. בטופס, עמודות מספריות מוגדרות LTR — `1.5-2` בשדה RTL מתהפך.

**מספרים ותאריכים.** docxtemplater מדביק מחרוזות ולא מעצב כלום. כל שדה במודל
מוגדר `string` בדיוק בגלל זה — העיצוב קורה לפני המיזוג.

## בדיקות

```bash
npm run typecheck
npm test                            # שלוש בדיקות המיזוג
```

| בדיקה | מה נבדק |
|---|---|
| `smoke-merge.ts` | מיזוג, לולאות, מסקנות, סדר הארכיון, אפס תגיות שנשארו |

| `smoke-wording.ts` | שלושת משפטי הפתיחה בכל סוגי הסקר, וההגנה על נוסח AI |
| `smoke-signatures.ts` | חתימה נכונה לכל שורה, ותא ריק למי שאין לו |
| `smoke-marks.ts` | סימון אדום → placeholder, שמירת עיצוב, הסרת צבע הסימון |
